# @kk-forge/oxlint-config

Shared oxlint configs for KK Forge's TypeScript packages.

Each preset owns one concern, so a package extends only the ones that describe it, and any combination works. Every preset that uses a `kk-forge` rule loads the plugin itself, and a config that extends several reports each problem once.

| Package                               | Presets                                                                           |
| ------------------------------------- | --------------------------------------------------------------------------------- |
| TypeScript library                    | `typescript.json`                                                                 |
| TypeScript library tested with vitest | `typescript.json`, `vitest.json`                                                  |
| Solid library                         | `typescript.json`, `solid.json`, `vitest.json`                                    |
| Node service or CLI                   | `typescript.json`, `layers.json`, `vitest.json`                                   |
| Solid web app                         | `typescript.json`, `solid.json`, `layers.json`, `vitest.json`                     |
| WXT extension with Solid              | `typescript.json`, `solid.json`, `layers.json`, `wxt.json`, `vitest.json`         |
| SolidStart app                        | `typescript.json`, `solid.json`, `layers.json`, `solid-start.json`, `vitest.json` |

- `typescript.json`, the language: the `correctness` category plus the rules it lacks that catch a bug or code that misleads its reader, type-aware, warnings fail. It turns on these besides:
  - The `no-unsafe-*` family and `no-unsafe-type-assertion`, so a value typed `any`, or cast to a type it was never checked against, cannot flow on unchecked. A value from outside, such as JSON or a message, gets a parser.
  - `only-throw-error` and `prefer-promise-reject-errors`, so every throw and rejection carries a stack.
  - `no-deprecated`, so a deprecated API is replaced when it is first used, not when it is removed.
  - The `no-unnecessary-*` family, `no-extraneous-class` and `import/no-named-as-default-member`: a cast, conversion, comparison, template or type parameter that changes nothing, a class of only statics, which is a module with extra syntax, and a default import read for a name the module also exports.
  - `eqeqeq`, keeping `== null`, which tests for both `null` and `undefined`. `curly`, so a guard is never one line without braces. `max-lines` at 450 lines of code, the size past which code-style.md splits a file. Blank lines and comments do not count, since they carry no logic. A flat command dispatch, which code-style.md measures by its longest arm, takes a disable comment with that reason.
  - `no-console`, everywhere but `src/infra/`, the one layer that writes output. core.md vendors the console sink into `src/infra/logger`. An entrypoint prints a CLI's result with `process.stdout.write`.
  - `no-alert`, so no native `alert`, `confirm` or `prompt` blocks the page: a library's window replaces each. `no-restricted-properties` on `innerHTML`, `outerHTML` and `insertAdjacentHTML`, since a string of HTML would run in the page: the text goes in as nodes. It also covers `self.alert`, `self.confirm` and `self.prompt`, which `no-alert` misses. `kk-forge/no-html-key` fails the key `innerHTML` or `outerHTML` in an object literal or as the key `Reflect.set` takes, as in `Object.assign(node, { innerHTML: text })` or `<div {...{ innerHTML: text }} />`, and Solid's `prop:innerHTML` and `prop:outerHTML` keys of a spread: such an object sets the property without reading it, so neither `no-restricted-properties` nor `solid/no-innerhtml` sees it. The rule reads the key as written, a name, a string, or a computed string or template without an expression, so a key computed from a variable passes. A test may set HTML from a string, since that page is one no user sees, and a native dialog stays banned in a test. oxlint replaces a rule's options rather than merging them, so in a test file the preset's override for tests also replaces a consumer's own `no-restricted-properties` list. A consumer that wants its restrictions in tests repeats them in an override of its own for `**/*.test.*`, `**/*.spec.*` and `**/tests/**`.
  - `import/no-unassigned-import`, so a side-effect import such as `import "./setup"` fails, since assembly is an explicit call. It allows `*.css`, and a `*.d.ts` file, where `import "x"` makes a module augmentation.
  - `kk-forge/no-index-files`, which rejects a file named `index.ts`, `index.tsx`, `index.js` or `index.jsx`, since tooling resolves that name implicitly. A module's surface is its `exports.ts`.

  A function that returns a value on one path and nothing on another hides a missing branch. The package's `tsconfig.json` sets `"noImplicitReturns": true`, which catches that, so the presets add no lint rule for it.

- `vitest.json`, the tests: the `vitest` plugin's correctness rules on `*.test.*` and `*.spec.*` files, which is vitest's own default include. They catch an assertion that never runs, never awaits or sits in a branch, a focused or skipped test, and a `vi.fn()` without its type, which is an `any` in the test. A test holds the typed mock itself, as in `const send = vi.fn<Port["send"]>(); const port = { send }; expect(send)…`, or `const send = vi.spyOn(port, "send")`. Reading `port.send` instead trips `typescript/unbound-method`, which `typescript.json` keeps on in tests too.
- `solid.json`, Solid and its JSX: eslint-plugin-solid's recommended rules, with `solid/no-innerhtml` refusing a static string too, `solid/no-unused-signal`, `solid/no-accessor-as-prop`, `solid/no-module-scope-reactive-primitive`, the `jsx-a11y` plugin's correctness rules, `kk-forge/no-conditional-map` and `kk-forge/no-inline-svg`. `jsx-a11y/control-has-associated-label` and `jsx-a11y/label-has-associated-control` look 4 levels deep, not the default 2, for a control's or a label's text (the label rule also for its nested control): Solid's `<Show>` and `<For>` each add a level, and text behind two of them read as missing. A signal or memo at module scope is global state that bypasses the composition root, so a component or the composition root creates it. `kk-forge/no-conditional-map` fails a `.map()` list in JSX children under a condition, such as `{open && rows.map(…)}`, `||`, `??` or `? :`. Solid reruns such an expression on any change and builds every row again, and `solid/prefer-for` catches only a `.map()` that is the whole expression. Render the list with `<For>` inside `<Show>`. `kk-forge/no-inline-svg` fails SVG markup in JSX, `<svg>`, `<path>` or any name in the `svg` namespace, since an icon lives in its own `.svg` file that a component imports. A drawing or a chart a project builds in JSX is that project's exception, with its reason. SVG inside a string is past the rule's reach.
- `wxt.json`, a WXT extension's entrypoints, under **WXT** below.
- `solid-start.json`, a SolidStart app's launchers, under **SolidStart** below.
- `layers.json`, an app's architecture: the layers `entrypoints → orchestration → features → entities → shared`. A file imports only layers to its right, and entities also each other. It reaches another module only through that module's `exports.ts`, or `exports.<entrypoint>.ts`, where `<entrypoint>` names a folder or file in `src/entrypoints`, such as `exports.background.ts` or `exports.overlay.content.ts`. A module that has a surface for an entrypoint serves that entrypoint through it. Each file or folder directly under `shared/` or `infra/` is a module of its own. A file is its own surface, and a folder is reached through its `exports.ts`. Only `entrypoints`, `infra` and a feature's `infra/` import the root `infra`, which takes `shared` alone.

  A feature's `infra/` folder holds the adapters only that feature needs. It is the feature's second surface: only the composition root, an entrypoint's `compose.ts`, imports it, through `features/<x>/infra/exports.ts`, and a test may too, a unit test beside the feature's code included. It imports of its own feature only the port, `port.ts` or a file in `port/`. Beyond the feature it imports the entities that port imports, the root `infra` and `shared`. The feature's other code does not import its `infra/`, and no other module does either.

  A test in a `tests/` folder whose parent folder holds `src/` may import any layer. For a nested `tests/` folder, the innermost one with a `src/` beside it counts. An import of the project's own src/ goes through `#/`, a subpath import that the nearest `package.json` declares in exactly one form, `"imports": { "#/*": "./src/*" }`. So `#/features/a/exports` names `src/features/a/exports`. A test helper in `tests/` beside `src/` goes through `#tests/`, declared as `"#tests/*": "./tests/*"`. Only tests and test kits import it: any other file under `src/`, `src/app.tsx` included, imports nothing from `tests/`, by `#tests/` or by path. In a monorepo, each app and package names its own `src/` this way. The rule fails four kinds of import. One is a `#/` import where the nearest `package.json` declares no such entry or maps `#/*` elsewhere, and the same for `#tests/`. Another goes through a different key of `imports`, such as `#src/*`. The third goes through `@/`, `~/`, `@@/` or `~~/`, the aliases a tool's config maps, WXT's included. The layer checks cannot see through those aliases. A `#` name that no key of `imports` matches, such as WXT's `#imports`, resolves through the `paths` of the importing file's nearest `tsconfig.json`, its `extends` included, as TypeScript resolves it. Any other name for the file's own `src/` fails too, since `#/` names it: a `paths` alias into it, or the app's own name. An import that none of these matches is a package's. The test reaches a module, an `infra` folder included, only through its `exports.ts` or an `exports.<entrypoint>.ts`. A `shared` or `infra` module that is one file is its own surface. The test may import any file of an entrypoint, which has no surface. A unit test inside `src/`, such as `foo.unit.test.ts` beside `foo.ts`, follows the rules of its module's other files, so it may import that module's internals.

  A feature's surface, its `exports.ts` and each `exports.<entrypoint>.ts`, gives out its components, its use cases, its error classes and types. The rule follows each name the surface exports to its declaration, through the files that re-export it. A component declares its return type `JSX.Element`. The use cases are the class `<X>UseCases` and its factory function `new<X>UseCases`, both in `features/<x>/<x>UseCases.ts`, where `<x>` is the feature's folder name exactly, such as `TextsUseCases` and `newTextsUseCases` in `features/texts/textsUseCases.ts`. A surface per runtime gives out a use cases class of its own, named for the runtime as well: for the `exports.serviceWorker.ts` of `features/convert`, the class `ConvertServiceWorkerUseCases` and its factory `newConvertServiceWorkerUseCases` in `convertUseCases.serviceWorker.ts`. Each word of the runtime's name, split at `.` and `-`, starts upper-case, so `exports.content-script.ts` gives `ContentScript`. An enum is a type here, whose members are its values. An error class passes too, since a caller matches it with `instanceof`: a class a file of the feature declares that extends the global `Error`, or another such class, followed through its imports. One the feature passes on from `shared` fails. A parent the rule cannot follow, such as a package's class or an expression, makes no error class. The rule fails any other value the surface exports, a free function, a constant or one from a package. In the use cases file, the constructor destructures one object typed `<X>UseCasesOptions`, as in `constructor({ retries, ...deps }: TextsUseCasesOptions)`, the factory takes that object, and the file exports no other value: a helper sits in a file of its own. The use cases file takes `.ts`, since it holds no JSX, and a `.tsx` one is reported as such. In an app with components, a feature that only shows has no use cases file. A UI that builds its DOM in TypeScript in place of JSX holds no components, so there `<X>UseCases` holds the showing, in a method such as `mount(root)`, and the surface gives it out. That a component holds no logic is for review to hold.

  An `entities` module is what two or more modules of `features`, `orchestration` and `entities` import. A type and its logic live in the one module that uses them, so the rule fails an `entities` module with fewer consumers and names the one there is. That entity moves into its consumer, or into a feature the consumer uses when it is an `orchestration` module, which holds no logic. An import from another entity counts, since an entity that entities share cannot move into a feature. `shared` imports no entity. A type import, a re-export and a dynamic import with a literal path count, a template literal without an expression included. An import from `entrypoints` does not count, since an entrypoint takes the type from the feature's surface. An import from a feature's `infra/` counts as that feature, and the root `infra` imports no entity. A test does not count either, because a test follows its code. An `orchestration` module builds one action from two or more features, so the rule fails one whose files import fewer than two `features` modules, and an entrypoint starts a single feature directly. Its tests do not count. That an orchestration module holds no logic of its own is for review to hold, since no import shows it. Both counts report on the module's file, or on the first file by name directly in its folder.

  An app that runs on several platforms keeps each platform's code in one adapter, `infra/<platform>`: `infra/chrome` for a browser extension and `infra/tauri` for desktop windows. Three rules hold the platforms apart:

  - A platform's SDK and its global APIs live only in its adapter.
  - Only the entrypoints of the platform's own runtime import its adapter. A root `infra` module, a feature's `infra/` and another runtime's entrypoint do not.
  - Code that needs a platform declares a port. The platform's adapter implements the port, and the composition root passes it in.

  For example, a feature's `infra/` that keeps its data in `chrome.storage` declares a port, a `KeyValueStore` with `get` and `set`, and takes it in its options. `infra/chrome` implements that port over `chrome.storage.local`, and the extension entrypoint's `compose.ts` passes the implementation in. A desktop entrypoint passes one from `infra/tauri`, so the feature runs on both.

  Both rules read the platforms from one table, one entry per platform: the adapter's folder under `infra`, the SDK's packages, the global APIs, and the entry API an entrypoint may take. The checks are the same for every entry, so a new platform is one entry in the table, and `layers.json` stays the one preset that checks them. `kk-forge/layers` checks the imports. It knows a platform by its adapter folder's name, and its SDK by package: `wxt` and its subpaths, `@wxt-dev/*`, `#imports` and `webextension-polyfill` are `chrome`'s, and `@tauri-apps/*` is `tauri`'s. An entrypoint takes from an SDK only the entry API that defines or mounts it, named in the import, from `#imports` or the WXT module that holds it: `defineBackground`, `defineContentScript`, `defineUnlistedScript`, the type `ContentScriptContext`, and `createShadowRootUi`, `createIntegratedUi` and `createIframeUi` with the types of the UI each returns and of its options. A Tauri window needs no such API, so an entrypoint takes nothing from `@tauri-apps/*`. A default, namespace, side-effect or dynamic import takes the whole SDK, which only its adapter does. A type-only import counts, since a port declares the types it needs, and so do a type such as `import("wxt/browser").Browser`, `import api = require("@tauri-apps/api")` and a call of the global `require` with a string. An entrypoint runs on one runtime, so it imports one platform's SDK and adapter. Its platforms are those its files import, and those of each other entrypoint they import, as a cumulative entrypoint does. An entrypoint with two fails on each import that brings one, and the report names a file that imports each. The check takes the linted file's imports as the editor shows them, saved or not, and reads the entrypoint's other files from disk, where it sees their static imports, re-exports and dynamic imports. A test is exempt, and so is a test kit, a file in a `testing` folder under `src/`, such as `src/shared/testing/`.

  A package adapter such as `@repo/logger/infra/chrome` also counts toward the entrypoint's platform. The check does not follow imports behind the package surface. `kk-forge/environment` checks the global APIs, below.

  `kk-forge/environment` fails, outside `infra` and a feature's `infra/`, what reads the clock and its timers, randomness or the environment: `Date.now()`, `new Date()` without a value, `Date()`, `performance.now()`, `setTimeout()`, `setInterval()`, `Math.random()`, `crypto.randomUUID()` and `crypto.getRandomValues()`, `process.env`, `import.meta.env` and `chrome.i18n`, whose interface strings reach logic through the facade in `shared`. It fails I/O and the browser's environment there too: `fetch`, `localStorage`, `sessionStorage`, `indexedDB`, `navigator` and `location`. Every one of these globals also counts through the global object, `globalThis`, `window` or `self`, as in `window.location`, `self.fetch`, `globalThis.window.fetch` or `window.crypto.randomUUID()`, when that name is the global and no local. A cast such as `(window as any)`, `satisfies` or `!` changes nothing, and neither does a string key, as in `window["fetch"]`. `document.location` is a property of `document`, not of the global object, so it passes. It matches the global a reference resolves to: a built-in, or a name no scope declares. So a parameter, an import or a local that shares the name passes, such as `const location = …`, and so does a type such as `typeof setTimeout` or `typeof navigator.clipboard`. A timer or one of those globals counts wherever the code names it, as in `const later = setTimeout` or `navigator.language`, and a member counts when destructured, as in `const { now } = Date` or `const { fetch: load } = window`. The same reads through Node's modules count, by module and name, with or without `node:`: `randomUUID`, `getRandomValues`, `randomBytes`, `randomInt`, `randomFill` and `randomFillSync` of `crypto`, `env` of `process`, the timers of `timers` and `timers/promises`, and `performance` of `perf_hooks`, also through a default or namespace import as in `crypto.randomUUID()`. An import of `fs`, `fs/promises` or `os` counts whatever it takes, since the first does I/O and the second reads the host. `process.argv` stays the entrypoint's, and a type-only import reads nothing. Logic takes the value as a parameter instead, and the composition root hands a `Clock`, a `Random` or the config to the code that needs one. In a package, the rule fails `process.env` and `import.meta.env` in `infra` and a feature's `infra/` too, also through `node:process`, since each app's composition root passes the package its config. A test is exempt. The console is `no-console`'s.

  `kk-forge/environment` also fails a platform's global API outside that platform's adapter, in `infra` and the entrypoints too: `chrome` and `browser` outside `infra/chrome`, and `__TAURI__` and `__TAURI_INTERNALS__` outside `infra/tauri`. It matches them as it matches the globals above, as a bare global, through the global object, as in `window.__TAURI__`, or destructured. A type that names one, such as `chrome.tabs.Tab`, counts too, since a port declares its own types. Outside `infra`, `chrome.i18n` gets one report, for the interface strings it reads. A test and a test kit are exempt.

  In a monorepo the rule also judges the imports between apps and packages. Its root's `package.json` declares `workspaces`, or the root holds a `pnpm-workspace.yaml`, and each app sits in `apps/<name>/` and each package in `packages/<name>/`, each with its own `package.json` and `src/`. The rule knows an app or a package by the `name` in its `package.json`, and an app without a `name` still counts as a user of the packages it imports. An app imports each surface of a package as it would its own layer: the bare name, `@repo/logger`, is the package's `shared`, and `@repo/logger/infra` is its `infra`, which only entrypoints, `infra` and a feature's `infra/` import. The first segment after the package name selects the layer. An import that the layer forbids gets the layer diagnostic first. Within an allowed layer, callers take the layer surface. Only a platform adapter has its own public subpath, such as `@repo/logger/infra/chrome`, and only entrypoints on that platform import it. A path that names no layer, such as `@repo/logger/testing`, is left alone. The rule fails an import into another app's source, by its name or by a path, any import of an app from a package, and an import into a package by a path, since an app or another package imports a package by its name. By default an app imports no other app. A project that needs this declares it in the rule's `apps` option, as one-way pairs of an app and the apps it may import: `"kk-forge/layers": ["error", { "apps": { "apps/a": ["apps/b"] } }]`. `apps/a` then imports `apps/b` only by name, as `@repo/b/features/x/exports`, through its `package.json` `"exports": { "./*": "./src/*" }`, the one form the rule reads. The import resolves to a file in `apps/b/src`, which the layer checks place as `apps/a`'s own: the layers, the module's surface, the platforms of an entrypoint, the counts of `entities` and `orchestration` and the declarations a feature's surface passes on. An entity of `apps/b` counts the modules of `apps/a` that import it as its consumers, named with their app, as `apps/a/features/x`. `exports` holds that one key alone. These fail: the reverse direction, an undeclared pair, a path in place of the name, the bare name, a segment Node refuses (such as `..`), and any other `exports` form. A package that only one app imports, and no other package, fails on the first of its source files by path, since it moves back into that app. A package nothing imports fails there too, with the advice to delete it. A package whose `package.json` holds `"layers": { "kind": "engine" }` is a technical engine, which stays a package with one app, so that count passes it when one app imports it. A repository without `apps/` publishes its packages, so that count leaves it alone. A test does not count as a use.

  A package may split a layer module into modules, as a technical engine splits `shared/model/` into `geometry/` and `geometry/points/`. Each such module is a folder with an `exports.ts` inside the layer module. Code of the layer module outside that folder imports it only through its `exports.ts`, and the outermost such folder it sits outside is the one it enters through. A feature holds no such modules, so its folders stay unjudged here. `typescript.json`'s `import/no-cycle` already fails a cycle between those modules.

  oxlint lints one file at a time, so the rule reads the imports of `features`, `orchestration` and `entities` from disk, and in a monorepo the imports of every app and package. In an editor, a report on a module changes only when the file it lands on is linted again.

## Use

```bash
npm install -D @kk-forge/oxlint-config oxlint oxlint-tsgolint
```

A Solid package also installs `eslint-plugin-solid` 0.20 or later. The presets need oxlint 1.90 and oxlint-tsgolint 7.0.2005 or later. oxlint resolves `extends` from the config's folder, so give the path:

```json
{
  "extends": [
    "./node_modules/@kk-forge/oxlint-config/typescript.json",
    "./node_modules/@kk-forge/oxlint-config/solid.json"
  ]
}
```

The package's lint script runs bare `oxlint`, and its fix script `oxlint --fix`, over the whole package. `.gitignore` and the config's `ignorePatterns` say what to skip, so tests, build scripts and tool configs are linted too. A folder list such as `oxlint src` leaves the rest unlinted, and no rule in a preset can see that.

The table above names the rest of `extends`. A library keeps `layers.json` too, since a package lays out its code in the same layers as an app. A package's own rules go below `extends` and win. A package's config holds only exceptions about its own files or names, each with its reason. A rule that would suit any package belongs in a preset.

## WXT

A WXT extension adds `"./node_modules/@kk-forge/oxlint-config/wxt.json"` to `extends`. Each entrypoint is then a folder `entrypoints/<name>/`, and WXT builds its `index.ts`. An HTML entrypoint's `index.html` loads `./index.ts` with a script tag, and `index.ts` mounts the page, as in `mountOptions()`. The rest of the entrypoint sits beside `index.ts` in the folder or in the layers.

- `kk-forge/wxt-entrypoint-folder` fails a script placed directly in a folder named `entrypoints`, such as `entrypoints/background.ts`. The rule reads the file's path, so it needs no glob from the package. oxlint reads no HTML, so review catches a flat `entrypoints/<name>.html`.
- For `**/entrypoints/*/index.ts` and `index.tsx`, `kk-forge/no-index-files` is off and `kk-forge/launcher` is on.

`kk-forge/launcher` allows imports and one line, which calls a function of the project, such as `startBackground()` or `mountOptions()`, where the logic lives. JSX is a call argument it rejects, so the file stays `index.ts`. Each form below holds one call: a named function called with identifiers, literals or property reads such as `ctx.signal`, which may stand under `void` or `await`. The line is one of these:

- The call itself, such as `mountOptions()`.
- The framework's definition around an arrow: `export default defineBackground(() => startBackground())`. The arrow's body is the call or a block that holds only the call, as in `async () => { await startBackground(); }`.
- The framework's definition around an options object: `export default defineContentScript({ matches: ["*://*/*"], main: (ctx) => mountOverlay(ctx) })`. One property is a function, written as an arrow, a method or `function`, whose body is the call or a block that holds only the call. Every other property holds a string, a number, a negative number, a boolean, `null`, a template without expressions, or an array or object of these.

In both definitions the function's parameters are plain names, with no defaults.

## SolidStart

A SolidStart app adds `"./node_modules/@kk-forge/oxlint-config/solid-start.json"` to `extends`. It turns on `kk-forge/launcher`, with its option `defaultExport`, for the files SolidStart requires: `src/app.tsx`, `src/entry-client.tsx` and `src/entry-server.tsx`, and each `.ts` and `.tsx` file under a folder named `routes`, where the file router finds the app's routes. The router skips a test there, and so does the rule.

SolidStart takes each of these files' default export as it is. WXT's own files keep only the forms under **WXT**, and `defaultExport` adds two more:

- A default export of the call itself, such as `export default startServer()`.
- A default export of a name the file imports as a value, such as `export default HomePage`. A type-only import binds no value.

A SolidStart app's files then look like this:

- `src/entry-server.tsx` holds `export default startServer()`, which composes the app and returns the server's handler, and `src/entry-client.tsx` holds `startClient()`.
- `src/app.tsx` and each page route hold `export default` of the component they import. SolidStart's route splitter drops `export { default } from`, so the rule rejects it.
- The rule rejects an API route's `export function GET()`: the server handler that `startServer()` returns answers such a request before the page render.

## From 13 to 14

- A Solid package raises `eslint-plugin-solid` to 0.20. The peer range no longer takes 0.19.
- `solid/no-module-scope-reactive-primitive` also reports `createDeferred` at module scope. A component or the composition root creates it, as it does a signal.
- `solid/reactivity` also reports a value read from a signal at setup that a declared handler captures when the component returns that handler, as in `const current = count(); const onClick = () => log(current); return <button onClick={onClick} />`. Read the signal inside the handler.
- `kk-forge/layers` holds an `infra` folder to its `exports.ts`, as it does a `shared` folder. An entrypoint, another `infra` module or a feature's `infra/` that imports a file inside `infra/<x>/` takes its `exports.ts`, or the `exports.<entrypoint>.ts` that serves that entrypoint, instead. A file directly under `infra/` stays its own surface.

## From 12 to 13

A project that `layers.json` checks moves to subpath imports:

- Declare `"imports": { "#/*": "./src/*" }` in the `package.json` of each app and package, beside its `src/`, and `"#tests/*": "./tests/*"` where its tests import helpers from `tests/`.
- Replace each import that goes through `@/`, `~/`, `@@/`, `~~/`, any other `#` key, or the app's own name with `#/` or `#tests/`, as in `#/features/a/exports`. A dynamic import counts, as `import("@/infra/x")` in a test does.
- Drop the `@/*` and `~/*` entries, and any other alias into `src/`, from each `tsconfig.json`'s `paths`, including one an eval or a tool reads. TypeScript 6 and later resolve `#/` through `package.json` with `moduleResolution` set to `bundler`, `node16` or `nodenext`, and Vite and Vitest read `imports` too, so the alias in `vite.config.ts` goes as well.
- Where one app must import another, declare the one-way pair in your own config, as `"kk-forge/layers": ["error", { "apps": { "apps/a": ["apps/b"] } }]`. `apps/b` declares `"exports": { "./*": "./src/*" }`, and `apps/a` imports it by name, as `@repo/b/features/x/exports`.

## From 4 to 5

- `kk-forge/one-line-entry` is now `kk-forge/launcher`, with no alias. A config that still names the old rule fails to load.
- `wxt.json` replaces the override a WXT package held for its `index.ts` files. Drop that override, and the flat-file override that turned the rule on for `entrypoints/<name>.ts`. Move each such file to `entrypoints/<name>/index.ts`.
- `typescript.json` turns on `import/no-unassigned-import`, allowing only `*.css`, and it is off in `*.d.ts`, where `import "x"` makes a module augmentation. A package drops its own copy of the rule. A side-effect import that assembles code, such as `import "./dependencies"`, becomes an explicit call.
- `typescript.json` and `solid.json` turn on the rules they list above that 4 lacked.
- A package with vitest tests adds `vitest.json`. Its `require-mock-type-parameters` reports each `vi.fn()` without a type parameter.
- `no-console` is allowed only in `src/shared/Logger.ts`. A logger elsewhere moves there.
- The package's `tsconfig.json` sets `"noImplicitReturns": true`, and its lint script runs bare `oxlint`.
- The peer versions rise to oxlint 1.90, oxlint-tsgolint 7.0.2005 and eslint-plugin-solid 0.19.

## Development

`mise run setup` installs the packages. `mise run check` type-checks, lints and formats, builds the plugin in `src/` into `dist/`, and runs the fixtures through the configs and the packed plugin.

## Release

Raise `version` in package.json and merge to main. A release that fails code the last release passed, such as a new rule, is a new major. CI publishes to npm once the `production` environment approves.
